### Incident Review: Host Reboot / Apparent OOM

- Reviewed system and workspace logs after Geoff reported the host appeared to run out of memory while he was flying back to LA.
- Timeline: DNS/network resolution failures began around 2026-06-27 13:32 UTC (`Temporary failure resolving`, `EAI_AGAIN`, `ERR_NAME_NOT_RESOLVED`) and affected apt/Ubuntu Pro, OpenAI/Moonshot failover, Brave search, GitHub, Whoop, and email sending.
- The host received an ACPI-style power event at 2026-06-27 14:31:38 UTC: `systemd-logind` logged `Power key pressed short` and `The system will power off now`. That points to host/control-plane initiated shutdown rather than an in-guest kernel panic.
- Reboot sequence: previous long boot ended at 14:31:47 UTC, a short boot ran 14:31:53-14:32:41 UTC, then current boot began 14:34:30 UTC. Current kernel is `6.17.0-1017-aws`; prior boot was `6.17.0-1013-aws`.
- Memory evidence: no kernel OOM panic before the shutdown. During shutdown, `user-1000.slice`/`user.slice` logged a process killed by the OOM killer, with `user@1000.service` peak around 3.4G RAM and 1.7G swap. OpenClaw gateway/user processes were close to the 3.7G RAM ceiling after restart too, so memory headroom is genuinely tight.
- Cron evidence: every 5 minutes, many `run_at_user_local_time.py` wrappers open simultaneously. Most exit quickly, but the fan-out creates noisy load and makes shutdown/restart harder. `cron.service` showed 1.6G memory peak over the boot.
- Disk was not the cause: root filesystem around 32% used; workspace logs small; largest artifact was a 1.5G Cigna MRF gzip under `data/`.
- Current recommendation: add explicit RAM/swap/DNS/reboot monitoring, stagger/consolidate cron, add `flock` around long jobs, configure reboot-required/control-plane event alerts, and strongly consider moving from 4GB RAM to 8GB RAM or reducing OpenClaw gateway worker/concurrency memory.
