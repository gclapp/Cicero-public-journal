# 2026-05-18 - Travel Task Duplicate Detection Fix

## Issue Reported
Geoff noticed duplicate travel tasks were created even after trips were already processed.

## Root Cause Analysis

### Problem 1: Two Competing Systems
- **Old system:** `travel_automation_v2.py` running via `travel_automation_cron.sh` at 9 AM and 9 PM PT daily
- **New system:** `calendar_travel_checker.py` running via `calendar-travel-checker-cron.sh` (was scheduled but not properly integrated)

Both systems were creating tasks independently without sharing state.

### Problem 2: Intermittent Todoist Connection Issues
The newer script sometimes showed `Found 0 existing tasks` even when tasks existed. This happens when:
- Todoist CLI times out (30s limit)
- Network connectivity issues
- API rate limiting

When this happened, the script relied on `processed_trips` state tracking, which worked correctly.

## Fixes Applied

### 1. Removed Old Travel Automation (CRITICAL)
- **Removed:** `0 9,21 * * * /home/ubuntu/.openclaw/workspace/scripts/travel_automation_cron.sh`
- This was the source of duplicates

### 2. Added New Travel Checker to Cron
- **Added:** `0 16 * * 1,3,5` (Mon/Wed/Fri at 9 AM PT)
- Runs `calendar-travel-checker-cron.sh`

### 3. Enhanced Duplicate Detection (3 Layers)
Updated `calendar_travel_checker.py` with three layers of protection:

**Layer 1: Processed Trips State (Most Reliable)**
- Uses `travel-checker-state.json` to track processed trip IDs
- Trip ID generated from flight summary + date
- Survives Todoist API failures

**Layer 2: Todoist Task Existence Check**
- Checks if main task name already exists in Todoist
- Catches cases where state was lost but tasks exist

**Layer 3: Fuzzy Pattern Matching**
- Checks for similar trip tasks (same destination + date pattern)
- Catches edge cases where task names might vary slightly

### 4. Added Lock File Protection
Updated `calendar-travel-checker-cron.sh` to prevent overlapping runs:
- Creates `/tmp/calendar_travel_checker.lock`
- Checks if another instance is running before starting
- Cleans up lock file on exit

### 5. Better Logging
- Added warnings when Todoist returns 0 tasks (indicates connection issue)
- Clearer log messages showing which duplicate detection layer triggered
- State tracking confirmation messages

## Verification

```

To prevent future duplicates:
1. **Never run both systems simultaneously** - Only `calendar_travel_checker.py` should be active
2. **Monitor logs** - Check for "Found 0 existing tasks" warnings
3. **State file backups** - The `processed_trips` array in state file is critical
4. **Test after any cron changes** - Verify only one travel job exists

# Location Detection Fix (Same Day)

## Issue Reported
Geoff is in New York but check-ins were showing weather for Los Angeles. The system wasn't using travel schedule to determine current location.

## Root Cause
The `detect_location_and_travel()` function in `heartbeat_sender.py` only checked for flights **today**, not ongoing travel. It didn't detect when Geoff was already at a destination based on hotel stays.

## Fix Applied

### Enhanced Location Detection
Updated `detect_location_and_travel()` to:

1. **Check for hotel stays first** — Looks for hotel events in calendar and determines if today falls within the stay period
2. **Detects location from hotel name/location** — Maps hotels to cities (NYC, Tahoe, SF, etc.)
3. **Then checks for flights today** — For departure/arrival detection
4. **Falls back to custody schedule** — Only if no travel detected

### Hotel Detection Logic
- Parses hotel stay dates from calendar events
- Checks if today falls within the stay period (start date + 4 days default)
- Maps hotel names/locations to cities:
  - "Westin New York at Times Square" → NYC
  - "Ritz-Carlton, Lake Tahoe" → Tahoe
  - "Westin Palo Alto" → Palo Alto

- `/home/ubuntu/.openclaw/workspace/scripts/heartbeat_sender.py` — Updated `detect_location_and_travel()` function

## Verification
Tested location detection:

```

Now correctly detects Geoff is in New York based on the hotel stay (The Westin New York at Times Square, May 17-21).

# Daily Schedule / Week View Fix (Same Day)

## Issue Reported
The daily update's "This Week" section only showed badges (✈️ FLIGHT, 🏨 HOTEL) but not actual event details. It also only showed today's events, not the full upcoming schedule including hotel stays and return flights.

## Root Cause
1. **Old `get_day_events()` function** only returned boolean flags (flight=True/False), not actual event details
2. **No hotel stay expansion** — Hotel events are single-day (check-in date) but represent multi-day stays
3. **Flight detection too narrow** — Only looked for "flight" keyword, missed "Delta Air Lines 742" style entries
4. **Bare `re.sub()` call** caused silent failures due to `except: pass` block

## Fix Applied

### New `get_week_events_detailed()` Function
Replaced the week view logic with a comprehensive function that:

1. **Collects hotel stays with date ranges** — Parses check-in dates and calculates checkout (4 days NYC, 3 days Tahoe, etc.)
2. **Expands hotel stays across all days** — Shows hotel for each day of the stay (Monday-Wednesday all show Westin NYC)
3. **Enhanced flight detection** — Checks for:
   - "flight" keyword
   - Airline names ("delta air lines", "united", "american airlines")
   - Flight number patterns (DL123, UA456, etc.)
4. **Smart route extraction** — Parses location field like "New York(JFK) - Los Angeles(LAX)" to show "JFK → LAX"
5. **Fixed regex issue** — Changed bare `re.sub()` to `__import__('re').sub()` to avoid scope issues
